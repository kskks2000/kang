# DEIMS 엔터프라이즈 수출입물류 데이터베이스

이 디렉터리는 PostgreSQL 11용 `deims` 엔터프라이즈 EIMS(수출입물류) 기준 스키마입니다. Firebase 로그인/IAM부터 조직·거래처·품목 마스터, 수입·수출 업무건, 상거래 주문, 국제운송·예약·컨테이너, 관세평가·신고·UNI-PASS, 보세·재고, FTA 원산지, 제재·전략물자·허가, 정산·회계·무역금융, 보험·클레임, 문서·워크플로·감사·분석까지 하나의 원자적 기준 마이그레이션으로 정의합니다.

현재 기준선은 번호가 붙은 13개 모듈, 611개 테이블입니다. 기존 물리 물류/WMS와 국제무역의 법적 상태를 함께 제공하지만 두 상태를 서로 추론하지 않도록 별도 원장과 증적으로 분리합니다. `security_role_template.sql`은 DBA 검토용 수동 템플릿이며 자동 적용 대상이 아닙니다.

## 핵심 업무 경계

`tenant_id`는 보안 경계, `trade_cases`는 수출입 업무건, `trade_shipments`는 국제운송, `customs_declarations`는 법적 신고, `shipments`와 재고 원장은 창고의 물리 실행입니다. 이 다섯 개를 하나의 상태나 테이블로 합치지 않습니다.

- Firebase 인증 성공은 신원 확인일 뿐입니다. 활성 `tenant_memberships`와 RBAC/범위/SoD 검증을 통과해야 테넌트 데이터에 접근합니다.
- 창고 입고·출고·이동 상태는 세관 수리나 원산지 적격성을 만들지 않습니다. 수리증적, 신고 버전, 품목별 수량 커버리지와 원산지 판정을 별도로 보존합니다.
- 신고·증명·보험증권·체크리스트는 논리 헤더와 버전/증적/이벤트로 분리합니다. 확정 후에는 직접 수정하지 않고 새 버전, 정정, 취소 또는 반대분개를 사용합니다.
- 제재목록은 사용한 버전을 고정하고 스크리닝 당시 주체 스냅샷을 보존합니다. 열린 `BLOCKING` hold는 예약 확정, 신고 제출, 국제선적 진행을 DB 트리거가 차단합니다.
- 라이선스·쿼터·원산지증명·보증·환급·정산·보험금은 사용/배부 원장을 두며 원수량이나 원금보다 많이 사용할 수 없습니다.
- 파일 본문과 비밀키·토큰은 DB에 저장하지 않습니다. 보호된 객체 저장소 URI, SHA-256, 크기, 버전, 마스킹된 요약만 저장합니다.

## 적용 전 필수 확인

- 대상은 PostgreSQL **11.x**와 `deims` 스키마입니다. 적용 스크립트는 다른 메이저 버전을 거부합니다.
- `kang.users(id)`가 먼저 존재해야 합니다. `deims.users.platform_user_id`는 이 플랫폼 사용자에 대한 필수·고유 FK입니다.
- 접속값은 루트 `.env`와 `backend/.env`를 읽는 기존 `backend/app/settings.py`를 사용합니다. 자격증명을 명령행, 로그, 문서 또는 Git diff에 출력하지 않습니다.
- 저장소의 DB 가드는 `211.47.74.33/dbkang`, 사용자 `kang`만 허용합니다. 가드를 완화하지 않습니다.
- 적용기는 연결 문자열뿐 아니라 실제 세션의 DB명·`current_user`·`session_user`·서버 IP·포트를 DDL 전에 다시 확인합니다.
- 현재 운영 PostgreSQL은 TLS 연결을 제공하지 않는 것으로 확인되었습니다. 실제 DEIMS 서비스 가동 전 서버 TLS/`hostssl`, CA 기반 `verify-full` 또는 승인된 VPN·사설망, 네트워크 허용 목록과 자격증명 회전을 완료해야 합니다.
- 전체 백업, 복구 연습, 예상 잠금 시간, 유지보수 창을 먼저 승인받습니다. `--dry-run`도 실제 DB에서 DDL을 실행한 뒤 롤백하므로 메타데이터 잠금을 획득합니다.
- 현재 배포 역할 `kang`은 `CREATEROLE`이 없습니다. 애플리케이션 역할은 스키마 적용과 별도로 DBA가 생성합니다.

## 적용과 검증

저장소 루트에서 실행합니다.

```powershell
# 실제 DDL을 한 트랜잭션에서 실행·검증한 뒤 전부 롤백
python .\scripts\apply_deims_schema.py --dry-run

# 승인된 유지보수 창에서 실제 커밋
python .\scripts\apply_deims_schema.py

# 배포된 카탈로그와 로컬 기준선 체크섬을 읽기 전용으로 재검증
python .\scripts\apply_deims_schema.py --verify-only
```

적용기는 다음을 검사합니다.

- 00–12 모듈이 정확히 한 개씩 존재하고 파일 순서가 완전한지
- 서버가 PostgreSQL 11인지
- 기준 테이블·명시적 인덱스·트리거, FK와 CHECK가 모두 존재하고 유효한지
- `row_version`/`updated_at`을 가진 모든 테이블에 갱신 트리거가 있는지
- 모든 `tenant_id` 테이블에 RLS·`FORCE ROW LEVEL SECURITY`와 읽기/쓰기 정책이 있는지
- `kang.users` 매핑, Firebase 주체 고유키, 허용 제공자(`password`, `google.com`) 및 비밀값 금지 컬럼/제약이 유지되는지
- `deims.schema_migrations`의 로컬 SQL 체크섬, PostgreSQL 카탈로그 구조 지문, 기준 시스템 시드 지문이 모두 배포 당시 값과 같은지

카탈로그 지문은 컬럼·제약·인덱스·트리거·함수·뷰·타입·RLS/정책을, 시드 지문은 기준 통화/국가/단위/운송/Incoterms/권한/시스템 역할/전역 상태/보존정책을 정렬된 형태로 고정합니다. 어느 단계든 실패하면 전체 트랜잭션을 롤백합니다. `--force-reapply`는 동일한 기준선을 다시 검증해야 하는 제한된 복구 상황에만 사용하며, 이미 기록된 체크섬과 다른 파일을 덮어쓰지는 못합니다.

## Firebase 로그인과 사용자 모델

- Firebase Admin SDK로 ID 토큰을 백엔드에서 먼저 검증한 후에만 DEIMS 세션/멤버십을 조회합니다.
- 정규 사용자 키는 `(firebase_project_id, COALESCE(firebase_tenant_id, ''), firebase_uid)`입니다. 이메일은 표시·검색값이며 계정 식별/자동 병합 키가 아닙니다.
- `auth_identities`는 Firebase의 `password`와 `google.com` 제공자 주체만 기록합니다. 비밀번호, Firebase ID/refresh token, Google access/refresh token은 저장하지 않습니다.
- 서로 다른 Firebase 주체 연결은 `account_link_requests`와 불변 `account_link_events`를 거치는 명시적·감사 가능한 절차입니다.
- 실제 테넌트 접근권한은 `tenant_memberships`, RBAC, 창고/파트너 범위 및 SoD 정책으로 부여합니다. Firebase 인증 성공만으로 테넌트 데이터 접근을 허용하지 않습니다.

## 다화주(3PL) 데이터 경계

`tenant_id`는 DEIMS 운영 조직/보안 경계이고, `warehouse_id`는 물리 운영 거점, `owner_partner_id`는 재고의 화주입니다. 세 값은 서로 대체할 수 없습니다.

- 같은 창고에 여러 화주의 동일 품목이 있어도 `stock_buckets`와 원장/잔고에서 화주를 분리합니다.
- FK 또는 동일 테넌트 참조 트리거가 다른 테넌트의 창고·화주·품목·작업 문서를 연결하지 못하게 합니다.
- 화주 이전은 기존 행의 `owner_partner_id` 변경이 아니라 승인된 이전/반대분개 거래로 기록합니다.
- 통합·정산·KPI에서도 가능한 한 테넌트/창고/화주 차원을 함께 보존합니다.

## 재고 이중분개 원장

재고의 사실 원천은 `inventory_transaction_headers`와 서명된 `inventory_transaction_entries`입니다. 거래는 품목/기준단위별 합계가 0이어야 하며, `stock_buckets` 간 이동으로 수량 보존을 표현합니다.

- 초안/검증 상태에서 항목을 구성한 뒤 `deims.post_inventory_transaction_for_tenant(uuid, uuid)`로만 게시합니다.
- 이 래퍼는 현재 테넌트, 활성 멤버십, 테넌트 수준 `inventory.post` 권한을 확인한 다음 내부 포스팅 함수를 호출합니다.
- `inventory_balances`는 게시 함수가 원장에서 투영하는 운영 캐시이며 직접 수정 대상이 아닙니다.
- 게시된 헤더/항목은 불변입니다. 오류는 원본을 수정·삭제하지 않고 정확한 반대분개 거래로 정정합니다.
- 예약·홀드도 별도 내역과 투영 제어를 사용합니다. DB 역할에서 잔고/게시원장 직접 DML을 허용하지 않습니다.
- 게시된 `RECEIPT` 거래의 모든 양수 물리재고 항목은 `receipt_inventory_allocations`가 입고라인별로 정확히 전량 커버하고, 입고 확정수량·품목·화주·단위·로트·시리얼 차원이 일치해야 합니다.
- 게시된 `SHIPMENT` 거래의 모든 음수 물리재고 항목은 `shipping_inventory_allocations`가 출고확정/선적라인별로 정확히 전량 커버합니다. 반대분개된 원본은 활성 출고수량에서 제외하되 불변 이력과 원장 대사는 유지합니다.

## 물리 재고와 보세 법적 상태

물리적 위치/수량과 관세법상 상태는 별도의 사실입니다.

- 일반 재고 원장은 로케이션/LPN/로트/시리얼과 물리 수량을 기록합니다.
- 보세 모듈은 `bonded_cargo*`, 보세 이동 그룹/항목, 법적 상태 이벤트, 반출입 신고와 수리 상태를 기록합니다.
- 각 보세 이동은 하나의 `BONDED_MOVE` 물리 재고 원장 항목과 1:1로 결합하며 테넌트·화주·품목·창고·로케이션·재고/법적 상태·로트·시리얼·LPN·기준단위·부호수량이 정확히 같아야 합니다. 반대로 게시된 `BONDED_MOVE`의 모든 물리 항목에도 게시된 보세 이동이 있어야 합니다.
- 이 수량 결합은 물리·법적 원장의 이탈을 막는 규칙이며, 물리 이동만으로 세관 수리·반출 승인을 추정하지 않습니다. 보세 반출입은 별도의 운영계 KCS/UNI-PASS 결과증적 또는 허용된 정식 예외승인을 계속 요구합니다.
- 보세 이동 그룹도 필요 시 화물/기준단위별 0 합계를 검증하고, 게시 후에는 반대 그룹/정정 버전으로만 수정합니다.

## UNI-PASS 연계 경계

이 스키마는 UNI-PASS 송수신의 연결 프로필, 신고 버전, 메시지 봉투, 상태 이벤트, 검증 오류 및 보호된 외부 객체의 URI/해시를 저장합니다. 실제 네트워크 어댑터, 인증서 개인키, 기관별 자격증명, 원문 XSD 전문은 포함하지 않습니다.

- 클라이언트 비밀, 인증서 개인키, access/refresh token은 승인된 secret manager/HSM에 두고 DB/로그에 평문 저장하지 않습니다.
- 대형 또는 규제 원문은 암호화된 객체 저장소에 보관하고 DB에는 URI, SHA-256, 크기, 스키마 버전 및 최소화된 진단만 기록합니다.
- XSD 버전과 코드표는 운영 배포 전에 관세청/UNI-PASS의 현재 공식 사양과 연계 승인 환경에서 검증해야 합니다.
- 재시도는 idempotency/correlation 키와 불변 메시지 이벤트를 사용합니다. 수신/수리/오류 상태를 기존 메시지 본문 덮어쓰기로 표현하지 않습니다.
- 실물 반출 증적은 활성 생산계 프로필에서 수신한 `ACCEPTED` 결과만 사용합니다. 단순 ACK, TEST/SANDBOX 프로필, 유효기간이 지난 프로필은 반출 근거가 될 수 없습니다.
- `customs_release_evidence`와 `customs_release_line_coverages`는 현재 봉인 신고버전·공식 결과메시지·출고라인을 연결합니다. 품목, 원산지, HS코드, 기준단위와 수량이 전부 일치하고 신고수량이 중복 소비되지 않아야 출고가 가능합니다.

## 정산과 회계 통제

계약/요율에서 생성된 `charge_events`와 `charges`는 청구서·세금계산서·정산으로 연결됩니다. 회계는 `journal_batches` → `journal_entries` → `journal_lines`로 구성하며 차변/대변 합계를 검증합니다. 배부·수납·관세 납부/환급은 부모 행 잠금, idempotency, 누적 상한과 원자적 헤더 투영을 사용해 동시 초과배부·이중지급을 막습니다. 게시/수리된 재무 및 세관 자료는 직접 변경하지 않고 승인된 취소·반전·신용/차변 문서 또는 새 버전을 사용합니다. 업무 승인자와 게시자의 분리는 RBAC, 승인 정책, SoD 위반 기록으로 운영해야 합니다.

## RLS와 런타임 역할

애플리케이션은 매 트랜잭션에서 Firebase 세션으로 확인한 테넌트를 설정합니다.

```sql
BEGIN;
SET LOCAL deims.tenant_id = '00000000-0000-0000-0000-000000000000';
-- tenant-scoped statements
COMMIT;
```

`deims.tenant_id`는 RLS 라우팅 컨텍스트일 뿐 보안 경계가 아닙니다. 임의 SQL 접속자는 값을 스스로 설정할 수 있으므로 다음 조건을 모두 지켜야 합니다.

- 런타임 역할은 `NOSUPERUSER`, `NOCREATEROLE`, `NOBYPASSRLS`이고 테이블/스키마 소유자가 아니어야 합니다.
- DB 접속은 검증된 백엔드에만 허용하고 브라우저/모바일 클라이언트에 자격증명을 배포하지 않습니다.
- 연결 풀은 트랜잭션마다 `SET LOCAL`을 실행하고 오류/반납 시 트랜잭션을 반드시 종료합니다.
- 기준선은 모든 `tenant_id` 기본 테이블에 `FORCE ROW LEVEL SECURITY`를 적용해 일반 소유자 DML에도 정책을 강제합니다. 재적용기는 advisory lock을 잡은 동일 트랜잭션 안에서만 잠시 `NO FORCE`로 전환하고 11의 마지막 블록에서 복구하며, 실패하면 전환도 롤백됩니다.
- 그래도 스키마 소유자/DBA 자격증명은 `ALTER TABLE ... NO FORCE ROW LEVEL SECURITY`를 실행할 수 있는 관리 권한입니다. 런타임에 소유자 계정을 사용하지 말고 별도 `NOBYPASSRLS` 역할을 사용하며, 소유자 자격증명은 DDL 전용으로 격리·감사합니다.
- 테넌트를 확정하기 전의 로그인 실패/플랫폼 감사(`tenant_id IS NULL`)와 전역 배치 실행은 일반 런타임 정책으로 기록할 수 없습니다. 수동 보안 템플릿의 `deims_platform_logger`, `deims_global_job_runner`를 각각 신뢰된 인증 로거/스케줄러 로그인에만 부여하고 연결 후 `SET ROLE`로 사용합니다. 역할명 검사와 테이블 ACL이 경계이며 임의 GUC가 경계가 아닙니다.
- PostgreSQL 11의 일반 뷰는 기반 테이블 RLS를 뷰 소유자 기준으로 평가할 수 있습니다. 스키마 소유자 뷰는 별도 감사·소유권 설계 전 런타임에 부여하지 않습니다.

DBA는 [`security_role_template.sql`](security_role_template.sql)을 검토해 런타임 그룹 역할과 허용 목록을 적용합니다. 템플릿은 모든 직접 권한을 먼저 제거하고 안전한 기준 조회와 테넌트 검증 재고 포스팅 래퍼만 허용합니다. 실제 서비스별 SELECT/INSERT/UPDATE 권한은 엔드포인트와 위협 모델을 검토한 뒤 더 좁은 역할로 추가합니다.

## 보존, 개인정보와 법적 검토

`data_retention_policies`의 시드는 기술적 출발점일 뿐 법률 의견이나 자동 폐기 명령이 아닙니다. 대한민국 관세·보세·외국환·전자세금계산서·상법/세법, 계약, 개인정보, 소송보존 의무는 회사 법무/세무/관세 전문가가 자료 유형별로 확정해야 합니다.

- `legal_holds`가 적용된 자료는 일반 보존 기간이 지나도 삭제/익명화하지 않습니다.
- 감사·접근·신고·원장 이벤트는 append-only이며, 비밀값과 불필요한 개인정보를 payload/JSON에 넣지 않습니다.
- 마스킹/익명화/아카이브 작업은 승인, 실행자 분리, 건수 대사, 복구 가능성 및 삭제 증적을 포함한 별도 배치로 구현합니다.
- 운영 전 백업 암호화, PITR, 복구 RTO/RPO, 객체 저장소 보존 잠금, 키 회전과 파기 절차를 검증합니다.

## PostgreSQL 11 지원 종료와 변경 원칙

PostgreSQL 11은 커뮤니티 지원이 종료된 버전입니다. 현재 호환성 때문에 11에 고정했지만, 보안 패치와 장기 운영을 위해 지원 중인 메이저 버전으로의 업그레이드 계획, 확장/드라이버 호환 시험, 복제·백업 전환 연습을 별도 프로젝트로 가져가야 합니다.

배포된 00–12 파일은 체크섬으로 잠긴 **불변 기준선**입니다. 운영 배포 후 기존 파일을 수정해 체크섬을 덮어쓰지 않습니다. 변경은 새 forward-only 마이그레이션 버전과 별도 체크섬으로 추가하고, 적용기에서 새 버전을 명시적으로 지원하도록 리뷰합니다. 파괴적 롤백 대신 보정 마이그레이션을 사용하고, 테이블/컬럼 삭제는 사용 중단·데이터 보존·백필·애플리케이션 전환을 거친 뒤 수행합니다.

## 이 스키마가 대신하지 않는 것

DDL만으로 실제 업무 통제나 법규 준수가 완성되지는 않습니다. 운영 전 다음이 별도로 필요합니다.

- Firebase 토큰 검증, 세션 고정/폐기, 권한 캐시 무효화가 포함된 백엔드 구현
- UNI-PASS 공식 연계 승인, 최신 XSD/코드표, 인증서/HSM, 장애·중복·재처리 시험
- 서비스별 DB 역할과 네트워크 접근통제, 비밀관리, 감사 로그 외부 반출/SIEM
- 대용량 데이터의 파티셔닝/아카이브 용량계획, 쿼리 플랜과 부하 시험
- 재고·보세·정산 대사 절차, 승인자 분리, 재해복구 훈련 및 법무/세무/관세 검토
